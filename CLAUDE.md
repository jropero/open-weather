# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 🚀 Overview

This repository is a high-fidelity, data-intensive biometeorological dashboard designed to monitor and predict the impact of atmospheric variables on human health. The core functionality is the scientific cross-referencing of real-time weather data (pressure, humidity, wind, temp) with physiological metrics, particularly focusing on **meteoropathy** and **migraine risk**.

The application is structured as a single-page, React/TypeScript application built with Vite, emphasizing a premium, highly responsive, and aesthetically complex user experience (dark glassmorphism, cinematic transitions).

## 🏗️ High-Level Architecture

The architecture is driven by sophisticated data presentation and scientific validation, requiring coordination across several distinct modules:

1.  **Data Ingestion Layer:**
    - **Source:** Primary data source is **Open-Meteo**, which provides access to the **Copernicus ERA5** database. This choice is critical as it enables the retrieval of extensive historical data (e.g., 1949, 1973, 2003 records) and accurate interday pressure delta calculations, necessary for scientific rigor (Atmospheric Memory module).
    - **Model selection:** For coordinates within Switzerland's bounding box (lat 45.8–47.8, lon 5.9–10.5), the forecast request appends `&models=meteoswiss_icon_ch2` to use the higher-resolution ICON-CH2-E model (~1 km grid). Outside Switzerland the default global model is used. The Swiss **daily** request asks for `models=meteoswiss_icon_ch2,best_match` (the API then returns every variable suffixed per model) and `mergeModelDaily()` (`src/utils/modelMerge.ts`) fills days ICON-CH2 doesn't cover (beyond today+4, returned as null) from the global `best_match`; hourly/current requests stay ICON-CH2-only. Logic lives in `getModelParam()` in `src/hooks/useWeather.ts`. Note: the correct approach is the `models=` query parameter on the standard `/v1/forecast` endpoint — a separate `/v1/meteoswiss` base URL does not exist.
    - **Loading, refresh & offline (`useWeather`):** returns `{ data, loading, refreshing, error, stale, fetchedAt, refresh }`. `loading` = first load of a location (full-screen loader); a refetch of the location already shown sets `refreshing` and keeps the data on screen. Auto-refresh when the data is older than `REFRESH_AFTER_MS` (30 min, matches the SW TTL): on `visibilitychange` → visible and on a 5-min interval while visible; plus on the `online` event when stale. A failed refresh keeps the data and sets `stale`; a failed first load falls back to `weather_last` (stale) and only shows the error screen (with Retry) when there is nothing to show. `StaleDataBanner` shows "Offline: data from HH:MM" + Retry.
    - **Request cancellation:** every fetch hook aborts its requests via `AbortController` when its inputs change or it unmounts (`useWeather` incl. historical + AQ, `useEnsembleData`, `useSeasonalForecast` via `fetchSeasonal({ signal })`, `OtherLocations`, `useGeoSearch`). Aborts are filtered with `isAbortError()` (`src/utils/fetchUtils.ts`) and never cached — `OtherLocations` also only caches complete (all-city) results. The ERA5 archive (`getERA5Data()` in `useHistoricalClimate.ts`, shared by the drill-down and `useAllPeriodRanks`) is instead **de-duplicated** with an in-flight promise map, because two consumers usually wait for the same request.
    - **Two-fetch split (timezone):** The forecast call is split into two parallel requests. **Fetch 1** (`timezone=UTC`): `current` (incl. `apparent_temperature` → `CurrentWeather.apparentTemperature`, null if missing; old `weather_last` entries lack it) + `hourly` (incl. `sunshine_duration` s/h → `SummaryHour.sunshine` and `is_day` → `SummaryHour.isDay`, `cloud_cover` % → `SummaryHour.cloudCover`, for the rain-strip sky icons; `direct_radiation` + `diffuse_radiation` W/m² (mean of the preceding hour) → `SummaryHour.directRadiation`/`diffuseRadiation` for the light strip, null when missing, `undefined` in old `weather_last`) — hourly timestamps are UTC strings and must be parsed with `+Z` throughout the app. **Fetch 2** (`timezone=auto`): all `daily` variables — using `auto` ensures daily aggregates (max/min temp, precip, sunshine, etc.) are bucketed by the _local_ calendar day, not UTC midnight (critical for Taipei, Auckland, etc.). The hourly window is **25 entries** (not 24) to correctly cover DST fallback days.
    - **Daily variables fetched:** `weather_code, temperature_2m_max, temperature_2m_min, pressure_msl_mean, relative_humidity_2m_mean, precipitation_sum, precipitation_probability_max, wind_speed_10m_max, sunshine_duration, precipitation_hours, sunrise, sunset`. `sunshine_duration` (seconds → display as hours) and `precipitation_hours` (integer hours) appear next to the day name in `FutureForecast`. `sunrise`/`sunset` come back as local-time strings from the `timezone=auto` call; `utc_offset_seconds` (also in the response) is used to convert them to UTC-equivalent strings so the existing `+Z` parsing in `App.tsx` and `DailyForecast` stays correct.
    - **Seasonal (long-range) source:** `https://seasonal-api.open-meteo.com/v1/seasonal` (separate host) — ECMWF **EC46** for `weekly=` (6 Monday-start weeks, updated daily ~20:30 UTC, week 1 starts in the past) and **SEAS5** for `monthly=` (calendar months starting at the _issue_ month, updated on the 5th). Always `forecast_days=215` so all 7 SEAS5 months come back even on the 1st–5th. Fetch/parse/build logic lives in `src/utils/seasonal.ts`; types (`SeasonalPeriod`, `SeasonalOutlook`, …) in `src/types/weather.ts`.
      - Fields used: `{temperature_2m,precipitation,pressure_msl,sunshine_duration,snowfall}_{mean,anomaly}`; weekly also `{temperature_2m,precipitation,pressure_msl}_anomaly_gt0` (% of the 51 members above normal). **Monthly has no probability/EFI fields** (the API returns HTTP 400 for them).
      - Weekly/monthly `*_mean` for precipitation (mm), sunshine (s) and snowfall (cm) are **period totals**, not daily means; temperature (°C) and pressure (hPa) are period means. Anomalies are vs. the model's hindcast climatology, not bias-corrected, 36 km area forecast.
      - `timezone=` is not sent — it doesn't change weekly/monthly period boundaries. "Today" is computed client-side in the location's timezone (`getLocalToday`).
      - Absolute temperatures are elevation-adjusted to the requested coordinate, so they differ slightly between nearby coordinates; anomalies don't.
2.  **State Management & Persistence:**
    - The application utilizes the browser's `localStorage` for persistent state. Keys in use:
      - `last_location` — the active location (survives reload).
      - `custom_locations` — user-saved geocoded locations; deletable from UI.
      - `other_locations_cache` — comparison panel data for all 12 predefined cities; 1-hour TTL. Cached as a whole so switching the active location still hits cache.
      - `hist_cache_{lat}_{lon}_{MM}-{DD}` — parsed historical data (1949/1973/2003) for a given location and calendar date. Date in the key is the invalidation mechanism (new day → new key). Entries from previous days are purged by `src/utils/cacheCleanup.ts`.
      - `seasonal_cache_{lat}_{lon}` — `{ run, timestamp, data }` parsed weekly + monthly seasonal data for the active location (Long-Range Outlook widget). Valid while `run` equals the expected EC46 run date (`getExpectedRun()`: UTC date of now − 22 h) and younger than 24 h. Purged by `cacheCleanup.ts` after 24 h.
      - `seasonal_trend_cache` — `{ [locationId]: { timestamp, data } }` monthly temp + precip for all 13 predefined cities (comparison panel trend). Per-city entries, 24-hour TTL; only successful fetches are stored. Bounded size, not purged.
      - `ensemble_cache_v2_${lat}_${lon}_${variable}` — `{ timestamp, times, members }` raw ECMWF IFS ensemble member matrix (control + 50 members, 15-day window, values rounded) per variable. 24-hour TTL, purged by `cacheCleanup.ts` (which also drops old un-versioned `ensemble_cache_*` keys). Populated on first drill-in to a weekly cell; week slices, stats and running totals are computed client-side.
      - `climate_hist_v2_${lat}_${lon}` — ERA5 daily archive (10 years, 5 variables) used by the climate history drill-down. 24-hour TTL. The `v2` suffix invalidates any stale `v1` entries written before the SEAS5 bias-correction fix.
      - `waking_window` — `{ start, end }` local hours (end exclusive, default `{ 7, 23 }`) for the Today & Tomorrow summary. Validated on read (`0 ≤ start < end ≤ 24`); not purged.
      - `cache_last_purged` — timestamp of the last cache cleanup run; cleanup fires at most once per 24 hours on app startup.
      - `language` — `'es' | 'en'`, the UI language (`LanguageContext.tsx`). Validated on read, default `es`; also mirrored to `<html lang>` (index.html ships `lang="es"`).
      - `weather_last` — `{ key: "${lat}_${lon}", fetchedAt, data }`, the last successful `WeatherData` of the **active location only** (one entry, ~30 KB, overwritten on every successful load incl. the async AQ/historical merges). Read only when a load fails (offline): the dashboard then shows it with the stale banner. Not purged.
3.  **Core Logic & Components:**
    - The `src/` directory houses all main components. Components are generally pure, rendering complex views based on derived biometeorological metrics (e.g., `PressureGauge.tsx`, `SevenDayChart.tsx`).
    - The logic for calculating the **Migraine Risk Index** and **Thom's Discomfort Index** resides in dedicated scientific utility files (expected within `src/utils` or similar organizational structure).
4.  **Styling & Theming:**
    - The entire UI is built using **Tailwind CSS v4** with a strong focus on accessibility (A11y high contrast) and cinematic, context-aware visual transitions (e.g., dynamic background gradients, glow effects).

## 📦 PWA (Progressive Web App)

The app is deployed at `ekult.co.uk/t` and is fully installable as a PWA on desktop and mobile (iOS/Android Chrome).

- **Base path:** `base: '/t/'` in `vite.config.ts` — must be an **absolute** path. Using `'./'` breaks the service worker scope registration.
- **Plugin:** `vite-plugin-pwa` with `registerType: 'autoUpdate'`. Generates `dist/sw.js` + `dist/workbox-*.js` alongside the app bundle.
- **Manifest:** `start_url`, `scope`, and `id` are all `/t/`. The icon is `favicon.svg` (`type: image/svg+xml`, `purpose: any maskable`).
- **Caching strategy:**
  - Open-Meteo forecast API → `NetworkFirst` with 30-minute TTL (fresh data preferred, offline fallback).
  - Open-Meteo Geocoding API → `CacheFirst` with 7-day TTL (location names rarely change).
  - Open-Meteo Seasonal API → `NetworkFirst` with 24-hour TTL. localStorage is the primary cache; the SW rule only adds an offline fallback.
- **Deploy:** copy the entire `dist/` output to the server's `/t/` directory. The SW must be served from the same scope — do not move `sw.js` into a subdirectory.

## ✨ Key Features & Areas of Focus

- **Data Visualization:** Expect advanced, multi-layered charts (Recharts) that display historical and forecasted weather data in a single, dense view. The `DailyForecast` composed chart uses the same card style as the ensemble chart (`<figure>` with a colour-key `<figcaption>` + swatch legend underneath, one muted `chart.hint` line): thin lines without dots (pressure red with a faint fill, temperature yellow, humidity a thin violet line on a hidden 0–100 % axis — no aurora background, wind dashed sky), square-topped rain bars, a visible slate **temperature** Y axis (right, °C on the top tick), midnight separators and a dashed "Ahora" line in hourly view; pressure has a hidden axis and the dashed `1013 hPa normal` line. Rain bars carry mm labels from `precipLabels()` (`src/utils/chartLabels.ts`): every wet day in daily view, only the peak within ±2 bars in hourly view (bars are ~13 px wide on phones). `DailyForecast` has a Daily/Hourly toggle; the hourly scrollable row shows per-card: time (UTC→local), weather icon, temperature, humidity, **wind speed**, precipitation/snow, and a comfort badge.
- **Seasonal index bar (right side of hero):** Above 10 °C shows the **FAT.** bar (Thom's Discomfort Index, 15–30 DI scale). Below 10 °C it switches to **POLAR/WCI** (Wind Chill Index), bar height mapped from +15 °C felt (floor) to −15 °C felt (ceiling), color-coded emerald→sky→blue→purple. The value is shown as an index (no `°`, like the FAT. DI number) with a `title` (`hero.wci.title`); tapping the gauge opens a popover that follows the mode: FAT. → Thom's index (DI + reasons), POLAR → the WCI (title `hero.wci.title`, `value · level`, formula/values/index bullets from `getWindChillIndex().reasons` — the third bullet is "Índice: X", deliberately not "Sensación" so it can't clash with the hero's single felt temperature — and a footer saying it is an index, not the felt temperature; sky accent instead of indigo). Popover body: `FatiguePopoverContent.tsx`. The standalone penguin section below the hero is separate and always shown in winter.
- **Scientific Alerting:** Alerting logic is based on multiple, converging variables (e.g., pressure drop _AND_ humidity threshold). Any change to this scientific model requires coordination between the _data layer_ and the _UI component_ responsible for rendering the alerts. Active alert types: migraine risk (0–6 pts), frost/ice overnight, tropical/torrida/ecuatorial night, precipitation onset.
- **Felt temperature:** `FeltTemp` is the single felt temperature in the hero; the penguin caption shows the same rounded value (wind-chill fallback).
- **Day / Night detection:** `isNight` is computed in `App.tsx` by comparing `Date.now()` against today's `sunrise`/`sunset` UTC timestamps (parsed with `+Z`). It is passed to `getWeatherInfo(code, lang, isNight)` in `src/utils/weatherCodes.ts` — WMO code 0 (clear) → `Moon` icon + dark indigo hero; codes 1/2/3 (cloudy) → `HeroIcon` (`src/components/HeroIcon.tsx`) renders `Cloud` + `Moon` as two separate layered elements (Moon absolutely positioned upper-right of Cloud) instead of the single `CloudMoon` icon, which looks poor when large. The hero icon is a full-opacity, inline 56 px (`strokeWidth` 1.25, `aria-hidden`) icon placed to the **right of the temperature number** in the centre of the gauges row (`<h2>`, then the small `FeltTemp` "SENS. 7°" stack showing current `apparent_temperature`, hidden when null/missing, then the icon; `flex items-center gap-1`; the Moon of the night-cloudy pair is 24 px, upper-right of the Cloud, positioned relative to it). The row gap is `gap-4 sm:gap-8` so it fits 360 px phones. `WeatherSvgEffects` also receives `isNight` to show a cool indigo glow instead of the warm sun haze for clear nights. Hourly cards in `DailyForecast` compute `isNightHour` per card from a `sunriseSunsetByDate` lookup keyed by `h.time.slice(0,10)`.
- **2-column widget layout:** `Presión y Humedad` and `Calidad del Aire` are in a `grid grid-cols-2 gap-3`. The pressure card gets `col-span-2` when air quality data is absent. Both cards use fully-opaque gradients (`from-white to-indigo-50` / `from-white to-emerald-50`) — avoid semi-transparent backgrounds that bleed the dark page colour through.
- **Calidad del Aire card & detail dialog:** Card shows AQI + badge + dominant pollutant chip (highest sub-AQI > 20), UV index row (`getUvInfo()`, 5 bands), PM2.5/PM10 dots, pollen badges, and a "Ver detalle →" button. Button mounts `AirQualityDetail.tsx` — a native `<dialog>` bottom sheet with: (1) 24h AQI bar chart (local timezone, color-coded by level); (2) per-pollutant sub-AQI rows (PM2.5, PM10, NO₂, O₃, SO₂) each with a level badge from `getAqiInfo()`, a fill bar, and a bilingual health-effect subtitle; (3) pollen list with grain counts. AQ fetch uses `forecast_days=2` and requests `european_aqi_pm2_5`, `european_aqi_pm10`, `european_aqi_nitrogen_dioxide`, `european_aqi_ozone`, `european_aqi_sulphur_dioxide`, `uv_index` in addition to the original fields. Dominant pollutant is computed client-side as the highest sub-AQI component. Pollen uses 4-level colour scale (≤10 green / ≤50 yellow / ≤200 orange / >200 red) matching the AQI badge colours.
- **FutureForecast (Próximos 3 Días):** Day name line shows ☀️ sunshine hours (`sunshineDuration / 3600`, amber-700) and 🌧 precipitation hours (`precipitationHours`, sky-700) when > 0. Secondary metrics row shows humidity (`💧`), rain probability (`🌂 X%`), and rain total (`🌧 Xmm`). Rain probability comes from `precipitation_probability_max` in the daily API response, stored as `DailyWeather.precipitationProbability`.
- **Hero alert tiles (`src/components/AlertBadges.tsx`):** mobile-first 2-column grid of tiles (icon + short word on top, value below; an odd last tile keeps one column's width, centered). Tiles are ranked by a fixed severity per alert (e.g. extreme storm > wind storm > ice > freezing rain > violent rain …; minor trends last); only the top 4 are shown, the rest behind a "+N más" toggle (never hides a single tile). **Urgent split:** `splitUrgent()` (`heroAlerts.ts`, pure, tested) takes alerts with severity ≥ `URGENT_MIN_SEVERITY` (70), highest first, max `URGENT_MAX_BANNERS` (2) out of the grid into full-width banners (`<AlertBadges part="urgent" />`, rendered under the condition/high-low and humidity/wind/sun lines, above the rain strip; red ≥ 85 else orange, lucide icon on a tinted chip, one soft `urgent-in` fade/scale on mount, none under reduced motion); extra severe alerts stay in the grid; both parts use the same split so an alert is never shown twice. Banners carry `data-urgent` (excluded from the e2e tile selector). Trivial alerts are dropped: the temperature tile only when |Δ| ≥ `TEMP_TREND_MIN_DELTA` (1.5 °C, `tempTrend()`), the wind tile only for strong/gale/storm (`isWindTileLevel()`; breezy gusts show in the metrics line). One tile per trend with time direction spelled out: pressure is the **past** 6 h (`↓4 hPa últ. 6h`, ⚡ when ≤ −3; falls back to 3 h), temperature the **next** 6 h (`↑3° próx. 6h`). Rain is **not** a tile — it lives in the rain strip below. Tapping any tile opens the Today & Tomorrow dialog (`onOpenDetails`, ref shared via `TodayTomorrowSummary`'s `dialogRef` prop) — `title` tooltips carry 3h/6h detail on desktop only. The inputs (`sumPrecip`, `getNightType`, `getFrostType`, `getPrecipOnset`, `getWindAlert`, `formatLeadTime`) are pure functions in `src/utils/heroAlerts.ts`. `getNightType` (local 20–06) and `getFrostType` (local 20–08) pick night hours in the **location's** timezone via `localHour()` (`data.timezone`, fallback `Location.timezone`, then the device zone).
- **Hero header, condition & metrics lines:** the weather-condition preview `<select>` (`PreviewSelect.tsx`, dev tool) only renders when the URL has a `preview` query parameter (`?preview`, read once); otherwise `previewCondition` stays `'auto'` and the location name gets the full width. `ConditionLine.tsx` shows the condition label plus today's high/low (`todayDaily.maxTemp/minTemp`, lucide `ArrowUp`/`ArrowDown`, rounded, hidden when missing/non-finite, sr-only "Máxima 9°, mínima 5°"; wraps whole onto its own centered line if long). `HeroMetrics.tsx` is one row of lucide icon + value items (`Droplets` humidity, `Wind` speed + direction + "· rachas N" when gusts ≥ `GUST_THRESHOLDS.breezy`, `Sun` "UV N" in the UV colour bands, hidden when `Math.round(uv) === 0`), thin dividers, `whitespace-nowrap` per item (whole items wrap, never split), full accessible labels in `aria-label`/`title` (`hero.metric.*`, `wind.from.N`). `SunEventLine.tsx`: next sun event ("Atardece 16:52" by day / "Amanece 07:48" at night) in the location's timezone, from the daily UTC-equivalent strings (`nextSunEvent()`, `formatClock()` in `heroAlerts.ts`); its own small centered line under the metrics row. Pure helpers in `src/utils/heroMetrics.ts`.
- **Freshness & pull-to-refresh:** `FreshnessLine.tsx` ("Actualizado HH:MM", device-local time from `fetchedAt`) under the hero is a button calling `refresh()` (spinning `RefreshCw` while `refreshing`, no spin under reduced motion); hidden while `StaleDataBanner` shows. `usePullToRefresh` + `PullIndicator.tsx`: at scroll top, no open `<dialog>`, a touch drag down > 70 px (`PULL_THRESHOLD`) refreshes on release; passive listeners only, `html { overscroll-behavior-y: contain }` disables the browser's own pull refresh; no-op on desktop.
- **MIGR. gauge level word:** below the score, `currentMigraineRisk.label` (MÍNIMO/BAJO/MOD/ALTO/EXTREMO) at 9 px uppercase in the gauge colour, in a zero-width wrapper so it never widens the column; full text in `title`.
- **Hero rain strip (`src/components/RainStrip.tsx`, logic `buildRainOutlook()` in `src/utils/daySummary.ts`):** between the humidity/wind line and the Today & Tomorrow teaser. **Fixed next 12 h** from the current hour (`RAIN_STRIP_HOURS`, not the waking window) from `summaryHours`. One sentence with the same umbrella verdict/wording as the dialog (`summary.umbrella.{level}.{kind}`) + spell times (`ahora–14h`, `desde 18h` when a spell runs past the window) + window total (mm, or cm for snow); below it one bar per hour (height √mm, full at 2.5 mm/h, min 25 %; opacity = probability; sky = rain, white = snow, indigo = freezing; missing data dashed, never drawn as dry; each wet bar has its mm amount (`fmtMm`, no unit) as a 9 px label on top of the bar; above each column an 11 px sky icon row (fixed height, `aria-hidden`): `RainStripHour.sky` — `sun` (lucide `Sun`, sunshine ≥ 30 min = `SUN_FULL_S` 1800 s), `partly` (`CloudSun`, ≥ 10 min = `SUN_SOME_S` 600 s), `cloud` (`Cloud`, dry daytime hour under 10 min); none for wet hours and missing data (missing sunshine is never 'cloud'; without `is_day`, only sunshine ≥ 10 min gives an icon). **Night** (`is_day` 0, dry) uses `cloud_cover` since sunshine is 0: ≤ 30 % `moon` (`Moon`, indigo), ≤ 70 % `moon_partly` (`CloudMoon`), above → `cloud`, missing → none (`NIGHT_CLEAR_MAX` / `NIGHT_PARTLY_MAX`). Moon hours count as clear for the dry variant but not in `sunHours`. Data = hourly `sunshine_duration` (s) + `is_day` from Fetch 1 → `SummaryHour.sunshine` / `isDay` (null when missing or absent in old `weather_last`). **Dry-clear variant:** a dry window (umbrella `none`) is still shown when ≥ 1 hour is clear (`sun`/`moon`) or partly (`partly`/`moon_partly`). `outlook.clearLevel` = `clear` when clear hours ≥ half of the known-sky hours (sky ≠ null) → header "Despejado"/"Clear" (`rain.strip.clear`), else `mixed` → "Nubes y claros"/"Partly cloudy" (`rain.strip.mixed`). Spell times (`clearRanges`, same `spells()` merging/"ahora–"/"desde" wording) use clear hours only at level `clear`, clear + partly at `mixed` (partly icons render in the row either way). Header icon = `outlook.headerSky`: the first clear hour's sky (amber `Sun` / indigo `Moon`), else the first partly hour's (`CloudSun` / `CloudMoon`). Top right: `outlook.sunHours` h + "sol próx. 12 h" only when > 0 (hidden for night-only); **no bar region at all** — only the 16 px icon row with the hour-label row directly under it (same column structure). Dry and fully cloudy/no data → hidden. Rainy window: unchanged apart from the icons, no sun total. No data → one line "Lluvia: sin datos". Tapping opens the Today & Tomorrow dialog. The teaser drops today's umbrella line (`getHighlights(…, { omitTodayUmbrella })`) only when the strip covers all remaining waking hours of today. `data-rain-strip` keeps it out of the e2e tile selector.
- **Hero light strip (`src/components/LightStrip.tsx`, logic `buildLightOutlook()` in `src/utils/daylight.ts`):** `<section data-light-strip>` (not a button) right after the rain strip, same glass card/width. Lux is an **estimate (±15 %)**: `estimateLux = direct*100 + diffuse*120` (lm/W efficacy), null if either radiation value is missing. ## 🧠 Dependencies and Utilities

- **Styling:** The component library uses modern Tailwind CSS utility classes extensively. New components should adhere to the existing glassmorphic, minimalist aesthetic.
