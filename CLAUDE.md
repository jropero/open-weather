# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 🚀 Overview
This repository is a high-fidelity, data-intensive biometeorological dashboard designed to monitor and predict the impact of atmospheric variables on human health. The core functionality is the scientific cross-referencing of real-time weather data (pressure, humidity, wind, temp) with physiological metrics, particularly focusing on **meteoropathy** and **migraine risk**.

The application is structured as a single-page, React/TypeScript application built with Vite, emphasizing a premium, highly responsive, and aesthetically complex user experience (dark glassmorphism, cinematic transitions).

## 🏗️ High-Level Architecture
The architecture is driven by sophisticated data presentation and scientific validation, requiring coordination across several distinct modules:

1.  **Data Ingestion Layer:**
    *   **Source:** Primary data source is **Open-Meteo**, which provides access to the **Copernicus ERA5** database. This choice is critical as it enables the retrieval of extensive historical data (e.g., 1949, 1973, 2003 records) and accurate interday pressure delta calculations, necessary for scientific rigor (Atmospheric Memory module).
    *   **Model selection:** For coordinates within Switzerland's bounding box (lat 45.8–47.8, lon 5.9–10.5), the forecast request appends `&models=meteoswiss_icon_ch2` to use the higher-resolution ICON-CH2-E model (~1 km grid). Outside Switzerland the default global model is used. Logic lives in `getModelParam()` in `src/hooks/useWeather.ts`. Note: the correct approach is the `models=` query parameter on the standard `/v1/forecast` endpoint — a separate `/v1/meteoswiss` base URL does not exist.
    *   **Two-fetch split (timezone):** The forecast call is split into two parallel requests. **Fetch 1** (`timezone=UTC`): `current` + `hourly` — hourly timestamps are UTC strings and must be parsed with `+Z` throughout the app. **Fetch 2** (`timezone=auto`): all `daily` variables — using `auto` ensures daily aggregates (max/min temp, precip, sunshine, etc.) are bucketed by the *local* calendar day, not UTC midnight (critical for Taipei, Auckland, etc.). The hourly window is **25 entries** (not 24) to correctly cover DST fallback days.
    *   **Daily variables fetched:** `weather_code, temperature_2m_max, temperature_2m_min, pressure_msl_mean, relative_humidity_2m_mean, precipitation_sum, precipitation_probability_max, wind_speed_10m_max, sunshine_duration, precipitation_hours, sunrise, sunset`. `sunshine_duration` (seconds → display as hours) and `precipitation_hours` (integer hours) appear next to the day name in `FutureForecast`. `sunrise`/`sunset` come back as local-time strings from the `timezone=auto` call; `utc_offset_seconds` (also in the response) is used to convert them to UTC-equivalent strings so the existing `+Z` parsing in `App.tsx` and `DailyForecast` stays correct.
    *   **Seasonal (long-range) source:** `https://seasonal-api.open-meteo.com/v1/seasonal` (separate host) — ECMWF **EC46** for `weekly=` (6 Monday-start weeks, updated daily ~20:30 UTC, week 1 starts in the past) and **SEAS5** for `monthly=` (calendar months starting at the *issue* month, updated on the 5th). Always `forecast_days=215` so all 7 SEAS5 months come back even on the 1st–5th. Fetch/parse/build logic lives in `src/utils/seasonal.ts`; types (`SeasonalPeriod`, `SeasonalOutlook`, …) in `src/types/weather.ts`.
        *   Fields used: `{temperature_2m,precipitation,pressure_msl,sunshine_duration,snowfall}_{mean,anomaly}`; weekly also `{temperature_2m,precipitation,pressure_msl}_anomaly_gt0` (% of the 51 members above normal). **Monthly has no probability/EFI fields** (the API returns HTTP 400 for them).
        *   Weekly/monthly `*_mean` for precipitation (mm), sunshine (s) and snowfall (cm) are **period totals**, not daily means; temperature (°C) and pressure (hPa) are period means. Anomalies are vs. the model's hindcast climatology, not bias-corrected, 36 km area forecast.
        *   `timezone=` is not sent — it doesn't change weekly/monthly period boundaries. "Today" is computed client-side in the location's timezone (`getLocalToday`).
        *   Absolute temperatures are elevation-adjusted to the requested coordinate, so they differ slightly between nearby coordinates; anomalies don't.
2.  **State Management & Persistence:**
    *   The application utilizes the browser's `localStorage` for persistent state. Keys in use:
        *   `last_location` — the active location (survives reload).
        *   `custom_locations` — user-saved geocoded locations; deletable from UI.
        *   `other_locations_cache` — comparison panel data for all 12 predefined cities; 1-hour TTL. Cached as a whole so switching the active location still hits cache.
        *   `hist_cache_{lat}_{lon}_{MM}-{DD}` — parsed historical data (1949/1973/2003) for a given location and calendar date. Date in the key is the invalidation mechanism (new day → new key). Entries from previous days are purged by `src/utils/cacheCleanup.ts`.
        *   `seasonal_cache_{lat}_{lon}` — `{ run, timestamp, data }` parsed weekly + monthly seasonal data for the active location (Long-Range Outlook widget). Valid while `run` equals the expected EC46 run date (`getExpectedRun()`: UTC date of now − 22 h) and younger than 24 h. Purged by `cacheCleanup.ts` after 24 h.
        *   `seasonal_trend_cache` — `{ [locationId]: { timestamp, data } }` monthly temp + precip for all 13 predefined cities (comparison panel trend). Per-city entries, 24-hour TTL; only successful fetches are stored. Bounded size, not purged.
        *   `ensemble_cache_${lat}_${lon}_${variable}` — raw ECMWF IFS ensemble response (50 members, 14-day window) per variable. 24-hour TTL. Populated on first drill-in to a weekly cell; member slices for a specific week are computed client-side.
        *   `climate_hist_v2_${lat}_${lon}` — ERA5 daily archive (10 years, 5 variables) used by the climate history drill-down. 24-hour TTL. The `v2` suffix invalidates any stale `v1` entries written before the SEAS5 bias-correction fix.
        *   `waking_window` — `{ start, end }` local hours (end exclusive, default `{ 7, 23 }`) for the Today & Tomorrow summary. Validated on read (`0 ≤ start < end ≤ 24`); not purged.
        *   `cache_last_purged` — timestamp of the last cache cleanup run; cleanup fires at most once per 24 hours on app startup.
3.  **Core Logic & Components:**
    *   The `src/` directory houses all main components. Components are generally pure, rendering complex views based on derived biometeorological metrics (e.g., `PressureGauge.tsx`, `SevenDayChart.tsx`).
    *   The logic for calculating the **Migraine Risk Index** and **Thom's Discomfort Index** resides in dedicated scientific utility files (expected within `src/utils` or similar organizational structure).
4.  **Styling & Theming:**
    *   The entire UI is built using **Tailwind CSS v4** with a strong focus on accessibility (A11y high contrast) and cinematic, context-aware visual transitions (e.g., dynamic background gradients, glow effects).

## 📦 PWA (Progressive Web App)
The app is deployed at `ekult.co.uk/t` and is fully installable as a PWA on desktop and mobile (iOS/Android Chrome).

*   **Base path:** `base: '/t/'` in `vite.config.ts` — must be an **absolute** path. Using `'./'` breaks the service worker scope registration.
*   **Plugin:** `vite-plugin-pwa` with `registerType: 'autoUpdate'`. Generates `dist/sw.js` + `dist/workbox-*.js` alongside the app bundle.
*   **Manifest:** `start_url`, `scope`, and `id` are all `/t/`. The icon is `favicon.svg` (`type: image/svg+xml`, `purpose: any maskable`).
*   **Caching strategy:**
    *   Open-Meteo forecast API → `NetworkFirst` with 30-minute TTL (fresh data preferred, offline fallback).
    *   Open-Meteo Geocoding API → `CacheFirst` with 7-day TTL (location names rarely change).
    *   Open-Meteo Seasonal API → `NetworkFirst` with 24-hour TTL. localStorage is the primary cache; the SW rule only adds an offline fallback.
*   **Deploy:** copy the entire `dist/` output to the server's `/t/` directory. The SW must be served from the same scope — do not move `sw.js` into a subdirectory.

## ✨ Key Features & Areas of Focus
*   **Data Visualization:** Expect advanced, multi-layered charts (Recharts) that display historical and forecasted weather data in a single, dense view. `DailyForecast` has a Daily/Hourly toggle; the hourly scrollable row shows per-card: time (UTC→local), weather icon, temperature, humidity, **wind speed**, precipitation/snow, and a comfort badge.
*   **Seasonal index bar (right side of hero):** Above 10 °C shows the **FAT.** bar (Thom's Discomfort Index, 15–30 DI scale). Below 10 °C it switches to **POLAR/WCI** (Wind Chill Index), bar height mapped from +15 °C felt (floor) to −15 °C felt (ceiling), color-coded emerald→sky→blue→purple. The standalone penguin section below the hero is separate and always shown in winter.
*   **Scientific Alerting:** Alerting logic is based on multiple, converging variables (e.g., pressure drop *AND* humidity threshold). Any change to this scientific model requires coordination between the *data layer* and the *UI component* responsible for rendering the alerts. Active alert types: migraine risk (0–6 pts), frost/ice overnight, tropical/torrida/ecuatorial night, precipitation onset.
*   **Day / Night detection:** `isNight` is computed in `App.tsx` by comparing `Date.now()` against today's `sunrise`/`sunset` UTC timestamps (parsed with `+Z`). It is passed to `getWeatherInfo(code, lang, isNight)` in `src/utils/weatherCodes.ts` — WMO code 0 (clear) → `Moon` icon + dark indigo hero; codes 1/2/3 (cloudy) → hero renders `Cloud` + `Moon` as two separate layered elements (Moon absolutely positioned upper-right of Cloud) instead of the single `CloudMoon` icon, which looks poor at 120 px. `WeatherSvgEffects` also receives `isNight` to show a cool indigo glow instead of the warm sun haze for clear nights. Hourly cards in `DailyForecast` compute `isNightHour` per card from a `sunriseSunsetByDate` lookup keyed by `h.time.slice(0,10)`.
*   **2-column widget layout:** `Presión y Humedad` and `Calidad del Aire` are in a `grid grid-cols-2 gap-3`. The pressure card gets `col-span-2` when air quality data is absent. Both cards use fully-opaque gradients (`from-white to-indigo-50` / `from-white to-emerald-50`) — avoid semi-transparent backgrounds that bleed the dark page colour through.
*   **FutureForecast (Próximos 3 Días):** Day name line shows ☀️ sunshine hours (`sunshineDuration / 3600`, amber-700) and 🌧 precipitation hours (`precipitationHours`, sky-700) when > 0. Secondary metrics row shows humidity (`💧`), rain probability (`🌂 X%`), and rain total (`🌧 Xmm`). Rain probability comes from `precipitation_probability_max` in the daily API response, stored as `DailyWeather.precipitationProbability`.
*   **Alert badge grouping:** Hero badges are split into semantic `flex flex-wrap` rows — (1) pressure+temperature trends, (2) precipitation onset + rain amounts, (3) wind, (4) night/frost/storm conditions. This prevents long vertical stacks in cities with many active alerts (e.g. Basilea, Taipei).
*   **Today & Tomorrow summary (`TodayTomorrowSummary.tsx`, logic in `src/utils/daySummary.ts`, hook `useWakingWindow`):** One teaser button in the hero (between the humidity/wind line and the alert badges) opens a native `<dialog>` (bottom sheet on mobile; Escape, focus trap and focus return are native) with an icon checklist per day. All verdicts use only the user's **waking window** (default 07–23, editable in the dialog footer, stored in `waking_window`), always in the **location's** local time (IANA `timezone` from the `timezone=auto` daily response, fallback `Location.timezone`). Today covers only the remaining waking hours (`Hoy (21–23h)`) and is hidden once the window is over.
    *   **Data:** `WeatherData.summaryHours` = the same hourly response as `hourly`, but current hour −25 h … +50 h and **nulls kept** (missing values are never read as 0). No extra request. `hourly` (25 entries) is unchanged.
    *   **Felt temp:** remaining-hours felt min/max. Tomorrow vs. today compares the felt **max of both full waking windows**; |Δ| < 2 °C → *similar*. Adjective depends on tomorrow's felt max (< 10 °C colder/milder, ≥ 25 °C hotter).
    *   **Umbrella (3 levels):** *wet* hour = ≥ 0.1 mm and probability ≥ 40 % (or probability missing); *take* if wet hours total ≥ 0.5 mm or include thunder (WMO 95/96/99); *maybe* if any hour has ≥ 0.1 mm at ≥ 15 % or probability ≥ 30 %; else *none*. Time ranges merge spells separated by one dry hour; > 2 spells are shown as one span "on and off". Snow / mixed / freezing wording from snowfall and WMO codes (same rules as `precipOnset`).
    *   **Wind:** same levels as the hero badge (`getGustLevel` / `GUST_THRESHOLDS` in `weatherCodes.ts`, shared with `windAlert`); the current gust reading is merged into the current hour. Below *breezy* (28 km/h) the row is omitted.
    *   **Health & air:** today reuses the hero's `currentMigraineRisk` (row from 2/6), the ⚡ 6 h pressure-drop rule (≤ −3 hPa), current AQI (> 40) and pollen (> 10), labelled as current readings. Tomorrow's migraine uses exactly `FutureForecast`'s inputs (`getTomorrowMigraine`). Air quality/pollen only exist for the current hour, so tomorrow always shows *no forecast*.
    *   **Night side notes** (outside the window, never affect verdicts): ≥ 1 mm rain or ≥ 0.5 cm snow (+ "wet roads" if it rains in the last 3 night hours), thunder, gusts ≥ 40 km/h, frost/ice (min ≤ 2 / ≤ 0 °C), tropical/torrid/equatorial night (same thresholds as `nightType`).
    *   **Teaser:** `getHighlights()` ranks candidates by fixed weights (thunder-umbrella > storm/gale wind > migraine 6/6 > umbrella > migraine ≥ 4 > strong wind > felt Δ ≥ 4 > felt Δ ≥ 2 > pressure drop / migraine 3 / poor air > maybe-umbrella > high pollen …; tomorrow −5), shows the top one plus a second if it weighs ≥ 30, else "nothing special · feels X–Y°".
*   **Long-Range Outlook (`LongRangeOutlook.tsx`, hook `useSeasonalForecast`):** Placed right after `FutureForecast` (timeline continues: hours → days → weeks → months → seasons). **Weather only — no health/migraine interpretation, not connected to alerting.** Expanded by default (chevron collapses it). Segmented control switches three tiers: *Próximas semanas* (EC46 weeks), *Próximos meses* (SEAS5 months), *Estaciones* (two columns: rest of current meteorological season + next full season, aggregated from monthly values — totals summed, means day-weighted).
    *   **Heatmap:** rows = temperature, precipitation, pressure, sunshine, snowfall; cells always show the **anomaly** (signed number + word like *más cálido*), diverging per-variable palette from `getAnomalyClass()`. There is no absolute-value toggle — SEAS5 absolute temperatures have a systematic cold bias and are not shown directly. Thresholds in `THRESHOLDS` (`seasonal.ts`): temp ±0.5/1.5 K, pressure ±1/4 hPa, precip/sunshine/snow relative to normal with per-day floors. Rows with no data are hidden; snowfall only shows when forecast or normal ≥ 0.05 cm/day.
    *   **Ensemble drill-down (all 6 weeks):** Clicking any weekly cell opens `EnsembleDetailView` — a full-screen native `<dialog>` that fetches `ecmwf_ifs025` (50 members) from `ensemble-api.open-meteo.com`. Shows a fan+spaghetti chart (50 thin lines + p10/p25/p75/p90 bands + bold mean) and a spread badge (✓ agree / ⚡ disagree / ⑂ bimodal). Variable switcher for temp/precip/pressure/wind. For weeks 3–6 (`weekIndex >= 2`) the component receives `lowConfidence={true}` and renders an amber banner: "Semana N: señal orientativa. La incertidumbre del ensemble es alta más allá de 14 días." Hook: `useEnsembleData`; stats: `src/utils/ensembleStats.ts`.
    *   **Climate history drill-down (months + seasons):** Clicking any cell in the months or seasons tiers opens `ClimateDetailView` — fetches 10 years of ERA5 daily data, aggregates to monthly/seasonal means, then compares against the SEAS5 forecast using **bias-corrected adjusted value = ERA5_10yr_mean + SEAS5_anomaly** (SEAS5 absolute temperatures are cold-biased by ~3 °C vs ERA5 for Alpine winters; this correction keeps the SEAS5 direction signal while expressing it on the observed scale). Shows: holistic plain-language summary, top-3 analogue years by z-score Euclidean distance, and a 80 px `MiniBarChart` per variable (Recharts ComposedChart, per-bar value labels, dashed ERA5-mean ReferenceLine, and a dashed slate-400 linear-regression trend Line over the 10 historical bars). Pressure is excluded — ERA5 provides `surface_pressure_mean`, SEAS5 provides `pressure_msl` on incompatible absolute scales. Hook: `useHistoricalClimate`; stats: `src/utils/climateStats.ts`. **Known limitation:** SEAS5 anomaly is relative to its 1993–2016 hindcast climatology; applying it over the 2016–2025 ERA5 mean (a warmer decade) may overestimate the adjusted value by ~0.5–1.5 °C. This is disclosed in a footnote inside the popup.
    *   **Inline temperature percentile rank:** When the months or seasons tier is open, a `useAllPeriodRanks` hook (`src/hooks/useAllPeriodRanks.ts`) fetches the ERA5 archive once in the background (same cache key `climate_hist_v2_*` as `ClimateDetailView`) and computes for each visible period: `forecastAdj = ERA5_mean + SEAS5_anomaly`, then `aboveCount = getAboveCount(forecastAdj, historicalTemps)`. Temperature cells show a third micro-line (e.g. `9/10`) when loaded, so users get the historical-rank insight without drilling in. Shown only when `above > 0 && above < total` to avoid edge-case zeroes.
    *   **Confidence:** weekly = mean ensemble agreement on the anomaly sign (temp/precip/pressure `_gt0`), ≥ 80 % high, ≥ 65 % medium, else low; weeks 3+ capped at medium. Monthly = lead time only (current & next month medium, later low; never high). Season = lowest of its months.
    *   **Partly-past periods:** week 1 (started last Monday) is shown and flagged *en curso*. The current month is shown (flagged) only if > 7 days remain; otherwise hidden (weeks tier covers it). Months entirely in the past (1st–5th, before the new SEAS5 issue) are dropped.
    *   **Seasons:** DJF/MAM/JJA/SON with hemisphere-correct names (Auckland: DJF = *Verano*). Tropics (|lat| < 23.44°, e.g. Santo Domingo) use neutral *trimestre* labels with month ranges plus a note. Header shows month coverage (`2/3 meses` + ⚠ when SEAS5 doesn't cover the whole season).
    *   **Attribution (mandatory, `SeasonalAttribution.tsx`):** visible footer with "Weather data by Open-Meteo.com" link (open-meteo.com/en/licence) and the ECMWF Terms-of-Use wording for services built on ECMWF data (statement, www.ecmwf.int, CC BY 4.0, modification note, disclaimer), plus models and SEAS5 issue month. Compact variant in the comparison panel.
    *   **Comparison panel trend (`useSeasonalTrends`):** `OtherLocations` makes **no seasonal request on load**. The *Cargar tendencia estacional* button fetches monthly temp + precip for all 13 predefined cities (one request each, so one failure doesn't affect the others); each row then shows the next full season (same `buildOutlook` as the widget) with temp/precip chips. Failed cities show an error and a *Reintentar* button that refetches only those. Cached 24 h in `seasonal_trend_cache`, restored on reload/location switch without a request.
*   **Predefined locations:** `src/constants/locations.ts` — includes Basilea, Parla, Madrid, Barcelona, Lagartera, Corral de Almaguer, Granada, Torrevieja, Santiago de Compostela, Reikiavik, Santo Domingo, Auckland, Taipéi.
*   **Custom location search:** `LocationSelector` uses `src/hooks/useGeoSearch.ts` to hit the Open-Meteo Geocoding API (`language=es`, debounced 300 ms) when the user types ≥ 2 chars. Results can be saved to `custom_locations` in localStorage (keyed by `custom_${lat}_${lon}`). Saved locations appear in a dedicated "Mis ubicaciones" section with a delete button. Deleting the active custom location falls back to the default (Basel).
*   **Performance:** The UI is optimized for high performance, minimal transitions, and mobile-first design, requiring careful handling of component rendering and CSS performance.

## 🧠 Dependencies and Utilities
